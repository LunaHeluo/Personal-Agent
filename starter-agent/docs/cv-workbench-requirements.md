# CV 工作台产品需求

## 文档信息

- 文档阶段：需求定义
- 产品名称：CV 工作台
- 目标仓库：Starter Agent
- 当前交互基准图：`docs/assets/cv-workbench-interaction-flow-v2.png`
- 历史视觉探索：`docs/assets/cv-workbench-interaction-design-v1.png`
- 前端风格：浅色卡片式桌面工作台
- 本文范围：产品需求、交互边界、数据需求与验收标准
- 本文不包含：详细技术设计、数据库 DDL、任务拆解或代码实现

## 1. 需求背景

Starter Agent 已具备求职 Chat、简历文件读取与版本保存、简历与 JD 对比、岗位调研、授权简历 RAG、Parent/Child Run、预算、取消、Trace、Artifact、Eval 和 Safety Gate 等基础能力，但当前产品形态仍以聊天页面和管理页面为主。

目标是将 Starter Agent 收敛为面向个人求职者的 CV 工作台，让用户围绕“目标岗位—岗位资料—简历版本—匹配证据—修改确认—投递记录—面试复盘”完成连续工作，而不是依赖多轮 Chat 记住业务状态。

工作台不是第二套 Agent 系统。它应复用现有 Runtime、Tool、RAG、任务委派、预算、Gate、Trace 和 Artifact 基础设施，在其上新增稳定的求职业务对象、专用 API 和可视化交互。

## 2. 产品目标

1. 用户能在一个工作台中管理求职目标、岗位、简历版本、匹配分析和投递进度。
2. 用户能基于指定岗位生成有简历证据支撑的修改建议，并逐条确认后保存新版本。
3. 用户能清楚区分事实、AI 建议、能力缺口和待人工确认项。
4. 后台 Agent 任务能够持久运行；刷新页面后仍可查看真实状态、预算、失败原因和部分结果。
5. 用户能追溯每个匹配结论和简历修改所使用的 JD 来源、简历证据和 Agent Run。
6. 工作台保持轻量、聚焦和低干扰，不把 Trust、Capability、MCP 等工程管理信息暴露为普通用户主流程。

## 3. 产品原则

### 3.1 证据优先

- 正向匹配必须引用授权简历证据。
- 岗位要求必须引用用户输入的 JD 或已验证岗位来源。
- 无证据的能力只能标记为缺失或待确认，不能由模型补写成经历。

### 3.2 用户控制

- AI 生成的简历修改不得静默应用。
- 保存正式简历版本、记录投递状态、发送材料或执行外部动作前必须取得用户确认。
- 用户可以逐条接受、拒绝或修改 AI 建议。

### 3.3 后端状态权威

- 岗位、简历版本、匹配分析、投递状态和 Agent Run 均以后端持久化数据为事实来源。
- 前端不得伪造任务完成、预算消耗、自动保存成功或投递成功。

### 3.4 复用现有安全边界

- 所有 Tool Call 继续经过现有 Pre-Tool-Call Gate。
- 简历与网页原文继续使用现有敏感数据、Artifact 和 Trace 治理。
- 不新增第二套 Agent Runtime、预算、取消、Trace 或权限系统。

### 3.5 渐进启用

- 用户粘贴 JD、导入 JD 文件和读取单个稳定 URL 可作为首版岗位入口。
- 多页面自动岗位调研只有在现有 Release Gate 通过且存在有效启用决策后才向普通用户开放。
- Multi-Agent 未启用时不得伪装为已运行，也不得在失败后静默回退旧网页 Workflow。

## 4. 功能范围

### 4.1 首版范围

- 求职目标与工作台首页。
- 简历库、简历版本和结构化简历编辑。
- 岗位库、JD 导入和岗位快照。
- 简历与岗位的匹配分析。
- 有证据的 AI 修改建议及人工审批。
- 版本差异、撤销和保存新版本。
- Parent/Child Agent 任务卡、状态、取消、恢复和安全详情。
- 简历 PDF/Word 预览与导出。
- 基础投递看板。
- 与现有 Chat、知识库、Run API、Trace 和 Artifact 的兼容。

### 4.2 后续范围

- 多模板简历排版。
- 面试复盘与问题库。
- 求职漏斗统计。
- 日历和邮箱联动。
- 招聘网站账号登录后的辅助操作。
- 团队协作或多人共享工作区。

### 4.3 明确不在范围内

- 未经确认自动投递岗位。
- 自动发送邮件、私信或联系 HR。
- 绕过登录、验证码、权限限制、robots 或站点禁止访问。
- 编造工作经历、学历、项目、技能或量化结果。
- 让前端直接访问 Child 原始对话、隐藏推理、原始 HTML 或受限 RAG 正文。
- 使用工作台 UI 绕过 Multi-Agent Release Gate。

## 5. 目标用户与使用场景

### 5.1 目标用户

- 正在集中求职的学生、应届生和初中级工程师。
- 需要针对多个岗位维护不同简历版本的求职者。
- 希望通过可验证证据而非泛化建议优化简历的用户。

### 5.2 核心场景

1. 用户创建“悉尼 Agent 工程师”求职目标，导入基础简历。
2. 用户粘贴 JD、输入稳定 URL，或在功能启用后启动岗位调研。
3. 系统建立岗位记录和不可变 JD 快照。
4. 系统读取授权简历证据并生成匹配点、能力缺口和来源冲突。
5. 用户在简历编辑器中查看 AI 修改建议及其证据。
6. 用户逐条接受修改，查看完整差异，并保存为新简历版本。
7. 用户导出该版本并记录对应岗位的投递状态。
8. 后台任务运行期间，用户可以离开页面、刷新、取消或在人工阻塞后恢复。

## 6. 信息架构

工作台顶部主导航至少包含：

- 工作台
- 档案
- 投递记录
- 面试复盘

“档案”统一承载面向求职者的长期资料：

- 简历档案与版本
- 岗位与 JD 快照
- 面试资料
- 导出文件

工程管理能力继续存在，但应放在设置或高级详情的次级入口：

- Agent 运行详情
- 知识库管理
- Agent 能力管理
- 模型、Tool 与 MCP 设置
- 信任中心

普通用户主流程不得要求理解 Specialist、Tool Schema、Policy ID 或 Child Trace 等内部概念；这些信息只在“运行详情/高级信息”中按需展示。

### 6.1 功能入口分级

| 能力 | 保留要求 | 普通用户入口 | 高级/管理入口 |
|---|---|---|---|
| Chat | 完整保留 | 左下角紧凑 `Starter Agent` 对话框 | Session 与消息详情 |
| 知识库 | 完整保留 | 以简历、JD、面试资料和证据引用的业务语言呈现 | 设置 → 知识库管理，可查看 Document、版本和 Chunk |
| 能力管理 | 完整保留 | 不进入普通求职主流程 | 设置 → Agent 能力，可管理 Skill、Tool、MCP 和启停状态 |
| 信任中心 | 完整保留 | 从建议证据、任务卡或运行详情进入安全摘要 | 设置/高级 → 信任中心，可查看 Eval、Trace 和 Safety |
| Parent/Child Run | 完整保留 | 任务进度、取消、恢复和失败摘要 | 运行详情中查看父子树、预算、Policy、Approval 和 Artifact |
| 邮件与确认 | 完整保留 | 在投递动作需要时按需出现 | 设置或审批记录 |

上述入口调整只改变信息架构与展示层级，不得删除后端 API、持久化数据、审计事件或安全校验。

## 7. 用户故事

- 作为求职者，我希望按目标城市和岗位方向组织工作区，以便聚焦当前求职计划。
- 作为求职者，我希望一个岗位始终对应可追溯的 JD 快照，以免分析结果随网页变化而失真。
- 作为求职者，我希望看到岗位要求与简历证据的一一对应关系，而不是只看到一个分数。
- 作为求职者，我希望 AI 修改以建议形式出现，并能逐条确认，而不是直接覆盖简历。
- 作为求职者，我希望保存新版本时保留来源版本、岗位和修改摘要。
- 作为求职者，我希望刷新页面后后台分析仍继续，并能看到真实进度和费用。
- 作为求职者，我希望取消任务后不再发生新的模型或网页调用，同时保留取消前证据。
- 作为求职者，我希望导出的 PDF 固定绑定一个简历版本，之后编辑不会改变已导出文件。
- 作为求职者，我希望每条投递记录能追溯到使用的岗位快照和简历版本。
- 作为求职者，我希望能力缺口保持为缺口，而不是被 AI 编造成我的经历。

## 8. 功能需求

### 8.1 工作台首页

1. 展示当前求职目标、目标状态、岗位数量、简历数量和待办数量。
2. 展示高优先级岗位、最近编辑简历、正在运行的 Agent 任务和近期投递事件。
3. 支持切换求职目标；不同目标的数据筛选状态相互隔离。
4. 空状态提供明确入口：导入简历、添加岗位、创建求职目标。
5. 首页统计必须来自持久化数据，不从聊天文本推断。

### 8.2 求职目标

每个求职目标至少包含：

- `workspace_id`
- 名称
- 目标岗位
- 目标城市/地区
- 远程偏好
- 经验级别
- 关键词和排除词
- 创建时间与更新时间
- 状态：进行中、暂停、归档

要求：

1. 用户可新建、编辑、暂停和归档目标。
2. 归档目标不删除关联岗位、简历版本、分析或投递记录。
3. 一个岗位可以关联多个目标，但每次匹配分析必须明确所属目标。

### 8.3 简历库

1. 支持导入 Markdown、文本和受支持的文档格式；首版编辑格式以结构化内容或 Markdown 为权威源。
2. 展示简历名称、目标方向、最新版本、更新时间和使用次数。
3. 支持创建基础简历、复制简历族、归档简历和查看版本历史。
4. 删除必须区分归档与永久删除；存在投递引用的版本不得直接永久删除。
5. 简历正文继续进入授权知识库；工作台数据库只保存必要业务字段和内容引用。

### 8.4 简历版本

每个版本至少包含：

- `resume_version_id`
- `resume_id`
- 版本号
- 来源版本 ID
- 内容引用与内容 Hash
- 关联岗位 ID，可为空
- 修改摘要
- 创建方式：用户编辑、AI 建议后确认、导入
- 创建时间
- 状态：草稿、正式、归档

要求：

1. 正式版本不可原地覆盖。
2. 新版本保存必须检查来源版本 Hash 或版本号，防止并发覆盖。
3. 相同幂等键和相同内容重复提交返回原版本；不同内容返回冲突。
4. 用户可比较任意两个同简历族版本。

### 8.5 结构化简历编辑器

1. 至少支持个人摘要、核心技能、项目经历、工作经历和教育经历区块。
2. 支持区块编辑、条目增删、排序和基础富文本格式。
3. 支持文本选择后的“改写、缩短、引用证据”操作。
4. 编辑过程自动保存为草稿，但不得自动创建正式版本。
5. 自动保存必须展示保存中、已保存、失败和版本冲突状态。
6. 支持撤销和重做；刷新页面后可恢复最近持久化草稿。
7. 编辑器不得允许 AI 在没有证据的情况下新增经历事实。

### 8.6 AI 修改建议

每条建议至少包含：

- `patch_id`
- 目标简历版本与区块
- 原文
- 建议文本
- 修改类型
- 修改理由
- 简历证据引用
- 岗位要求引用
- 风险或缺失提示
- 状态：待确认、已接受、已拒绝、已失效

要求：

1. AI 生成建议时不直接修改简历正文。
2. 用户可以逐条接受、拒绝或手动编辑后接受。
3. 支持“查看差异”和“全部应用”；全部应用仍必须由用户主动触发。
4. 来源版本变化后，未应用建议必须重新校验；不能安全应用时标记失效。
5. 接受建议后先更新草稿，只有保存新版本后才成为正式版本内容。
6. 能力缺口不得自动转化为正向经历描述。

### 8.7 岗位库

岗位至少包含：

- `job_id`
- 标题、公司、地点、工作方式
- 来源 URL 和最终 URL
- JD 快照引用与内容 Hash
- 职责、必要要求、加分项
- 获取时间和更新时间
- 验证状态
- 用户状态：待分析、已收藏、已忽略、已归档
- 关联求职目标

要求：

1. 支持粘贴 JD、导入 JD 文件、输入单个稳定 URL。
2. 自动岗位调研只在 Release Gate 允许时展示并执行。
3. 同一来源或同一内容 Hash 的岗位应去重；冲突来源不得静默覆盖。
4. 岗位页面失效后保留最近一次合法快照，并明确标记时效风险。
5. 支持按优先级、分数、公司、地点、状态和更新时间筛选。

### 8.8 匹配分析

匹配分析至少包含：

- `match_analysis_id`
- 岗位 ID 和 JD 快照 Hash
- 简历版本 ID 和内容 Hash
- 求职目标 ID
- 总分和评分规则版本
- 匹配要求
- 简历证据
- 能力缺口
- 来源冲突
- 建议动作
- Parent/Child Run 引用
- 创建时间和失效状态

要求：

1. 匹配必须绑定具体岗位快照和具体简历版本。
2. 总分必须能解释，至少展示评分维度及其证据覆盖情况。
3. 正向匹配必须具备授权 `chunk_id/source_ref`。
4. 缺少证据时标记 missing；来源不一致时标记 conflict。
5. 用户切换简历版本或岗位快照后，旧分析仍可查看，但标记为已过期。
6. 重新分析不得覆盖旧分析记录。
7. 前端只展示已通过 Result Validator 的标准化结果。

### 8.9 CV Agent 协作面板

1. 协作面板固定在左侧栏下方，并以紧凑卡片或可折叠面板呈现，不得占据主工作区。
2. 默认展开高度只容纳最近一条 Agent 消息、快捷操作、任务摘要和输入框；用户可折叠或打开完整会话。
3. 协作面板默认只作用于当前工作台、岗位和简历版本。
4. 输入框展示当前作用域，例如“仅当前简历”或“当前岗位与简历”。
5. 用户可粘贴 JD、招聘链接，或提出改写、分析、解释证据和生成摘要请求。
6. 提供与当前状态相关的快捷操作，例如“查看差异”“重新评分”“搜索相似岗位”。
7. 面板必须区分普通问答、后台任务、待确认修改和失败结果。
8. Agent 不得自动扩大作用域访问其他简历、岗位、长期记忆或知识库。
9. Chat 可以继续存在，但业务结果必须写入工作台对象，而不是只保留在消息正文中。
10. 后台任务在面板内显示真实进度和取消入口，但完整 Parent/Child 详情按需打开，不直接铺满对话框。

### 8.10 Agent 运行状态

1. 发起后台分析时展示任务卡，至少包含：
   - Parent Run 状态和阶段
   - Child 完成数/总数
   - 当前动作摘要
   - Token、费用、时间、模型调用和工具调用预算
   - 开始时间和最近更新时间
   - 取消按钮
2. 运行状态必须通过现有 Run API 和 SSE 获取。
3. 页面刷新、切换页面或 SSE 重连后能够从后端恢复状态。
4. `waiting_for_user` 时展示安全继续入口和明确原因。
5. 终态停止 SSE 重连。
6. 失败、超时、取消和预算耗尽不得伪装成成功，也不得自动应用业务结果。
7. 用户可打开高级详情查看 Parent/Child 树、缺失项、冲突和安全摘要；原始日志和隐藏推理不可见。

### 8.11 PDF/Word 预览与导出

1. 首版至少提供一个 ATS 友好的浅色简历模板。
2. 预览与导出必须绑定具体 `resume_version_id`。
3. PDF 应支持中文字体、稳定分页、链接和可复制文本。
4. Word 应以 DOCX 格式导出，保留标题、列表、段落、链接和基础分页结构，并能在主流办公软件中继续编辑。
5. 待确认版本不得导出；用户确认新版本后才启用“导出 PDF”“导出 Word”和“保存到档案”。
6. 导出不得改变简历版本。
7. 导出文件保存为受控 Artifact，并记录内容 Hash、格式、模板版本和生成时间。
8. 相同版本、格式、模板和设置的重复导出应支持幂等复用。

### 8.12 投递看板

投递记录至少包含：

- `application_id`
- 岗位 ID
- 简历版本 ID
- 当前状态
- 优先级
- 创建时间、投递时间和更新时间
- 下一步行动和提醒时间
- 状态事件时间线

状态至少包括：

- 待决定
- 待投递
- 已投递
- 笔试
- 面试
- Offer
- 拒绝
- 撤回
- 归档

要求：

1. 记录或修改投递状态必须由用户确认。
2. 投递记录必须保留使用的岗位快照和简历版本。
3. 状态变更追加事件，不静默覆盖历史。
4. 首版不自动向外部网站投递。

### 8.13 面试复盘

1. 用户可为投递记录创建面试轮次。
2. 支持记录问题、回答摘要、反馈、结果和待改进项。
3. AI 可以总结和分类用户提供的面试记录，但不得虚构面试事实。
4. 面试缺口可以生成学习或简历检查建议，但不能自动改写正式简历。
5. 音频转写、日历和邮件联动不作为首版必需能力。

### 8.14 搜索、筛选与通知

1. 简历、岗位和投递记录支持关键词搜索。
2. 筛选条件应保留在当前工作台会话中。
3. 仅对需要用户处理的事件显示通知，例如任务完成、人工阻塞、版本冲突和导出失败。
4. 不使用高频动画或重复 Toast 干扰用户。

### 8.15 现有平台能力保留与集成

#### 知识库

1. 现有知识库上传、文档版本、Chunk、检索、Citation 和授权范围继续保留。
2. 上传简历后，前端在“简历档案”中创建业务记录，并通过引用关联知识库 Document/Version；不得复制形成互不一致的第二份知识库正文。
3. 普通用户默认看到“简历证据”“岗位来源”等业务名称；`chunk_id`、索引状态和解析详情仅在证据详情或知识库管理中显示。
4. 删除或归档档案前必须检查简历版本、投递记录、匹配分析和 Artifact 引用。

#### Agent 能力管理

1. 现有 Skill、Tool、MCP、Registry、启停、审核、Policy 和依赖健康能力继续保留。
2. 能力管理不出现在普通工作台主导航，统一放入“设置 → Agent 能力”。
3. 普通用户可看到功能级可用性，例如“自动岗位搜索暂不可用”，但不得直接修改 Tool 权限或 Specialist Prompt。
4. 管理入口的启停操作继续经过现有身份、Policy、审核和 Trace 机制。

#### 信任中心

1. 现有 Eval、Trace、Safety、Release Gate 和父子运行关联继续保留。
2. 工作台中的每个匹配分析、AI 修改、岗位来源和导出 Artifact 应能跳转到对应的安全证据摘要。
3. 普通用户只看到脱敏摘要、证据状态和失败原因；工程级 Trace、Policy ID、Approval ID、Tool Call 和版本信息在高级详情中展示。
4. 工作台重构不得降低现有 Trace 的父任务、子任务、Tool、Policy、Approval 和 Artifact 关联完整性。

#### 保留功能的导航与兼容

1. “设置”至少包含“知识库管理”“Agent 能力”“模型与工具”“信任中心”。
2. 现有知识库、Capability、Trust、邮件和 Run API 保持兼容；如需版本升级，应提供明确迁移，不得由新前端调用私有内部接口。
3. 普通 Chat 可通过左下角 Agent 面板继续使用；管理页面仍可通过设置或直接路由访问。
4. 前端隐藏入口不等于停用能力；后端启停状态必须来自现有 Registry、Policy 和 Release Decision。

## 9. 浅色卡片式前端要求

### 9.1 视觉基调

- 页面背景使用暖白或浅灰白，不使用纯白大面积直铺。
- 内容区域使用白色或轻微暖色卡片。
- 主色为低饱和深绿色；成功使用浅薄荷绿；警告使用柔和琥珀色；错误使用克制的珊瑚红。
- 文字使用深灰而非纯黑，次要文字保持足够对比度。
- 阴影轻微，主要依赖边框、留白和层级区分卡片。
- 不使用大面积渐变、玻璃拟态、3D 光效或装饰性插画干扰主任务。

### 9.2 布局

桌面工作台采用“左侧工作栏 + 右侧主工作区”的总体布局；右侧主工作区内部可以包含上下文候选栏：

1. 左侧工作栏上部：用户档案指标、上传简历、创建档案和简历版本列表。
2. 左侧工作栏下部：缩小后的 `Starter Agent` 对话框、快捷操作、后台任务摘要和取消入口。
3. 右侧主区域：匹配分析、定制简历和档案详情，为视觉主区域。
4. 右侧上下文栏：Agent 搜索的候选岗位、来源链接、选择框及“评估并留存”操作。

要求：

- 右侧匹配/简历区域始终为视觉主区域。
- 左侧 Agent 对话框不得高于左侧栏可视区域的一半，且不得挤压档案的基本操作。
- 候选岗位栏可折叠；折叠后保留已选数量和待确认提示。
- 页面顶部提供全局导航和当前用户入口。
- 主要操作固定在可预测位置，避免滚动后丢失保存、取消和审批入口。

### 9.3 关键交互流程实现

页面应以可见步骤表达完整流程：

`上传简历 → 选择 JD → 匹配评估 → 确认修改 → 导出留存`

要求：

1. 步骤条必须区分已完成、当前和未开始状态，并能返回已完成步骤查看数据。
2. 上传的简历立即出现在左侧档案中；解析或入库未完成时显示处理中状态，不伪装成可分析。
3. 用户粘贴的 JD 在保存岗位快照前展示来源与内容确认。
4. Agent 搜索产生的链接只进入候选区，不自动进入岗位档案、不自动评分、不自动产生投递记录。
5. 用户勾选候选并点击“评估并留存”后，系统才创建岗位记录、保存经确认的 JD 快照并发起匹配分析。
6. 候选卡至少展示岗位名、公司、地点、来源域名、“打开链接”“查看 JD”和选择框。
7. 评分页至少展示总分、岗位、公司、地点、JD 确认状态、来源、匹配亮点、能力缺口和 Agent 修改建议。
8. 修改建议以“原始内容 → 建议内容 → 证据来源 → 状态”形式展示，支持逐条确认。
9. Agent 生成的新简历以新的待确认版本进入档案，不覆盖当前使用版本。
10. 待确认版本显示“查看完整差异”“继续修改”“确认版本”；只有确认后才开放 PDF、Word 和保存到档案操作。
11. “确认版本”与“评估并留存”均属于明确用户动作，不能由模型消息、SSE 事件或前端自动触发。

### 9.4 卡片规范

- 卡片圆角建议为 10–14px。
- 卡片边框使用浅暖灰；普通卡片不使用明显投影。
- 选中卡片使用绿色边框、左侧强调线或浅绿色背景，但不得同时使用过多强调效果。
- 成功、缺口、冲突和等待确认必须使用颜色、图标和文本三种信号中的至少两种，不能只依赖颜色。
- 卡片内部信息遵循“标题—状态—摘要—动作”顺序。

### 9.5 交互状态

所有可交互组件至少具有：

- 默认
- Hover
- Focus
- Active/Selected
- Disabled
- Loading
- Success
- Error

异步操作要求：

- 操作提交后立即提供可见反馈。
- 超过 300ms 的操作显示加载状态。
- 后台任务不使用无限全屏 Loading，应显示持久任务卡。
- 保存失败时保留用户输入并允许重试。

### 9.6 响应式与可访问性

- 首要支持宽度不低于 1280px 的桌面浏览器。
- 1024–1279px 时允许折叠左栏或右栏。
- 小于 1024px 时可降级为单栏页面和抽屉，不要求首版提供完整移动端编辑体验。
- 关键文本和控件满足 WCAG AA 对比度目标。
- 所有操作可通过键盘访问，并具有可见 Focus 状态。
- 图标按钮必须提供可访问名称。
- 动画尊重 `prefers-reduced-motion`。

## 10. 数据与所有权要求

### 10.1 工作台业务数据

工作台数据库负责保存：

- 求职目标
- 简历和版本元数据
- 结构化草稿及 Patch 状态
- 岗位和 JD 快照元数据
- 匹配分析
- 投递记录和状态事件
- 面试复盘
- 与 Run、Artifact、知识库的引用关系

### 10.2 现有基础设施继续负责

- Session 与 Chat 消息
- Parent/Child Run、任务状态和预算
- Tool Gate、Policy 和 Approval
- 原始网页与 Tool Artifact
- 简历知识库、Document、Chunk 和 Citation
- Trace、Eval 和 Safety Gate

### 10.3 跨域引用

- 业务对象优先保存 `parent_run_id`、`child_run_id`、`artifact_id`、`knowledge_base_id`、`document_id`、`chunk_id` 和内容 Hash。
- 不得为方便而把完整简历、原始 JD、网页 HTML 或 Child 对话复制到多个业务表。
- 删除或归档业务对象不得破坏仍被投递、导出或 Trace 引用的不可变版本。

## 11. 非功能需求

### 11.1 安全与隐私

- 简历、联系方式、面试记录和投递状态按敏感个人数据处理。
- 前端 API 必须使用可信用户身份，不接受请求体自报 principal 作为授权依据。
- 受限 Artifact 正文只通过现有授权读取路径访问。
- 公共事件、SSE 和日志不得包含简历全文、原始 HTML、Cookie、Token 或隐藏推理。
- 导出 PDF 和下载链接应具有访问控制和合理有效期。

### 11.2 可靠性

- 自动保存、Patch 应用、版本保存、投递状态变更和导出均需要幂等键。
- 并发编辑使用版本号、ETag 或内容 Hash 检测冲突。
- 页面刷新和应用重启后可恢复草稿、任务和待确认状态。
- 状态变更失败不得出现“前端成功、后端未保存”的假象。

### 11.3 性能

- 工作台首屏在本地正常环境下应在 2 秒内显示可交互骨架和已缓存业务数据。
- 常规列表接口应分页，默认每页不超过 50 项。
- 简历编辑输入不应因 AI 请求阻塞。
- Agent 分析、PDF 导出和大文件处理均作为可观察异步任务运行。

### 11.4 可观测性

- 关键业务操作记录业务对象 ID、Run ID、版本号、幂等键和安全结果。
- 用户可见错误使用稳定错误码和可操作提示。
- 工程人员可从业务对象追溯到 Parent/Child、Tool、Policy、Approval、Artifact 和 Trace。

### 11.5 兼容性

- 现有普通 Chat、知识库、邮件、Capability 和 Trust 管理功能保持可用。
- 新前端只调整这些能力的入口和业务表达，不删除已有管理 API、审计数据或安全规则。
- 知识库、Agent 能力和信任中心必须能够通过设置或高级详情到达，并保持基于可信身份的访问控制。
- 工作台不直接调用已禁止的旧岗位网页 Workflow。
- Multi-Agent 关闭时，工作台仍可完成手工 JD 导入、简历匹配、修改审批和版本保存。

## 12. 验收标准

### 12.1 工作台基础流程

1. 用户能够创建求职目标并导入一份基础简历。
2. 刷新页面后，求职目标、简历和当前草稿仍存在。
3. 用户能够添加一个手工 JD 并建立岗位快照。
4. 用户能够选择具体简历版本和岗位发起匹配分析。
5. 分析结果展示匹配证据、能力缺口、冲突和来源。

### 12.2 AI 修改流程

1. AI 建议不直接改变简历正文。
2. 每条正向建议包含简历证据和岗位要求引用。
3. 用户拒绝建议后，建议不进入草稿。
4. 用户接受建议后，草稿变化可在版本差异中查看。
5. 保存后创建新版本，旧版本内容保持不变。
6. 来源版本已变化时，旧 Patch 被拒绝或标记失效。

### 12.3 Agent 运行流程

1. 发起后台分析后返回真实 `parent_run_id` 并显示任务卡。
2. 页面刷新后任务卡恢复，状态与 Run API 一致。
3. SSE 断开重连不会重复业务写入或重复显示事件。
4. 用户取消后不再产生新的模型或 Tool 调用，取消前证据仍可审计。
5. `waiting_for_user` 能展示原因并通过授权入口安全恢复。
6. 失败、超时和预算耗尽不生成成功匹配或自动修改。

### 12.4 PDF/Word 与投递

1. 待确认版本的 PDF/Word 导出按钮不可用，并说明需要先确认版本。
2. 用户确认版本后，能够导出指定简历版本 PDF 和 Word。
3. PDF 可复制文字、中文显示正确、分页无明显截断；DOCX 可继续编辑且基本结构完整。
4. 导出后继续编辑简历不会改变原 PDF/DOCX Artifact。
5. 投递记录必须绑定岗位快照和简历版本。
6. 投递状态变更经过确认，并保留完整时间线。

### 12.5 前端视觉与可用性

1. 桌面端采用浅色卡片布局，左侧为档案与紧凑 Agent，右侧为主要工作区域及候选岗位栏。
2. 选中岗位、匹配成功、能力缺口、冲突和待确认状态可明确区分。
3. 不依赖颜色作为唯一状态提示。
4. 保存、取消、查看差异和审批入口在主要流程中无需超过两次点击。
5. 键盘可访问主要导航、列表、编辑和审批控件。

### 12.6 保留能力与入口

1. 工作台重构后，普通 Chat、知识库、能力管理、信任中心、邮件和 Parent/Child 运行详情仍可访问。
2. 左下角 Agent 面板可以发起普通 Chat，并能打开完整会话；业务结果同步进入工作台对象。
3. 上传简历可在档案中查看，同时在知识库管理中存在对应 Document/Version 引用。
4. 设置中的 Agent 能力页能读取现有 Skill、Tool、MCP 和启停状态，但未经授权不能修改。
5. 工作台匹配结果能进入脱敏信任摘要，高级用户可继续追溯 Parent/Child、Policy、Approval、Artifact 和 Trace。
6. 隐藏管理入口不会改变后端实际启停或 Release Gate 状态。

### 12.7 Multi-Agent 边界

1. 没有有效 Release Decision 时，自动多页面调研入口隐藏或明确不可用。
2. 关闭状态不影响手工 JD 和单稳定 URL 流程。
3. 启用后，符合条件的调研必须走真实 Parent/Child 路径，并展示预算和 Child 状态。
4. 失败时不得自动回退旧网页 Workflow。

## 13. 必验场景

| 场景 | 预期结果 |
|---|---|
| 首次进入无数据 | 显示导入简历、添加岗位和创建目标的空状态，不显示虚假统计 |
| 自动保存失败 | 保留编辑内容，显示失败与重试，不显示“已保存” |
| 同时编辑冲突 | 后提交者收到版本冲突，可比较并重新应用，不覆盖先提交内容 |
| Patch 来源版本过期 | Patch 标记失效，不应用到新版本 |
| 无简历证据 | 结果标记 missing，不生成正向经历 |
| JD 来源冲突 | 并列展示来源与冲突，不静默选择一个值 |
| Agent 部分成功 | 展示 partial、已有证据和缺失项，不补齐失败字段 |
| Agent 取消 | 停止后续调用，不回填成功结果，保留审计证据 |
| SSE 重复事件 | 通过事件序号去重，不重复卡片或状态事件 |
| PDF/Word 重复导出 | 相同输入幂等复用或生成同内容 Hash，不重复计费 |
| Agent 搜索返回候选 | 只显示候选和来源；用户未点击“评估并留存”前不创建岗位、不评分、不写档案 |
| 新简历待确认 | 新版本进入档案并标记待确认；确认前 PDF/Word 导出不可用 |
| 管理入口降级 | 知识库、能力管理和信任中心不占主导航，但可从设置或高级详情安全访问 |
| 投递状态重复提交 | 相同幂等键只产生一个状态事件 |
| Multi-Agent 未启用 | 自动调研不可执行，手工 JD 流程仍正常 |

## 14. 风险与待确认事项

1. **简历编辑格式**：首版是结构化 JSON、Markdown 区块还是二者组合，需要在设计阶段冻结权威格式。
2. **文档导入**：DOCX/PDF 的版式保真和结构提取准确率需要单独验证；首版可限制为 Markdown/文本加人工校对。
3. **评分模型**：匹配总分的维度、权重和版本管理需要产品定义，不能只依赖模型自由评分。
4. **PDF/Word 引擎**：需要选择支持中文字体、分页和可复制文本的 PDF 渲染方案，以及结构稳定、可继续编辑的 DOCX 生成方案。
5. **工作台数据库**：业务表与现有 Session Store、Knowledge Store、Run Store 的事务和引用边界需要技术设计。
6. **多目标数据隔离**：同一岗位和简历在多个求职目标中的复用与分析隔离需要冻结规则。
7. **真实网页调研**：当前真实 Playwright Smoke 仍有环境阻塞记录；未解决前不能把自动调研标记为正式可用。
8. **Release Gate**：当前没有满足默认启用条件的有效 Multi-Agent 决策，工作台必须保持 fail-closed。
9. **前端演进方式**：现有单文件 `src/web/index.html` 是否继续扩展，还是迁移到组件化前端，需要在设计阶段决定。
10. **数据迁移**：现有 Markdown 简历、Knowledge Document、岗位候选和 Chat 消息如何映射到工作台对象，需要提供可重复、可回滚的迁移方案。

## 15. 首版完成定义

首版完成必须同时满足：

1. 用户可以完成“导入简历—选择或确认 JD—匹配分析—审批修改—保存版本—导出 PDF/Word”的闭环。
2. 所有正向匹配和 AI 修改均可追溯到岗位来源与授权简历证据。
3. 后台任务状态可恢复、可取消、可追踪，且复用现有 Parent/Child 基础设施。
4. 浅色卡片式工作台达到桌面端可用标准；左侧档案与紧凑 Agent、右侧分析与候选岗位区域符合当前交互基准图，并满足关键可访问性要求。
5. Multi-Agent 未通过门槛时保持关闭，不影响首版核心闭环。
6. 现有 Chat、知识库、Agent 能力、Trust、邮件、Run API 和普通 Agent 路径无回归。
