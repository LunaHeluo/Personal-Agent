# Shanghai Bilingual Agent/AI Job Search Design

## Goal

Improve recall and ordering for Shanghai Agent/AI job searches without relying on prompt wording alone. The production workflow must search both `上海` and `Shanghai`, combine Google Jobs and ordinary Google organic results, rank locally relevant Chinese and English job-detail pages consistently, and preserve transparent diagnostics through JD retrieval and output rendering.

## Current-State Diagnosis

The current implementation has four root causes:

1. `JobResearchOrchestrator.search_prepared` sends only the single query generated by the search-profile model.
2. `SearchJobsSerpApiTool` accepts only `query`, `location`, and `limit`; it does not expose or send `hl`, `gl`, or `google_domain`.
3. Ordinary Google organic search is conditional: it runs only when Google Jobs yields no usable candidates or fewer candidates than the requested limit.
4. Candidate ordering gives structured link kinds priority before relevance score, so English Google Jobs results can outrank more relevant Shanghai Chinese organic detail pages.

The output layer also reports the total partial-result count while rendering only the first three, and partial results omit their search snippet.

## Scope

This change covers:

- deterministic Shanghai query planning;
- localized SerpAPI requests;
- bounded parallel Google Jobs and organic discovery;
- cross-query aggregation, URL deduplication, mirror preference, and ranking;
- Chinese JD section recognition;
- mixed-result output and search diagnostics;
- fixed-fixture before/after recall reporting.

It does not add a general translation service or unbounded query generation. Other Chinese cities may reuse the abstractions later, but only Shanghai behavior is required here.

## Query Planning

Location and role wording are independent dimensions. The planner must not assume Chinese role terms require a Chinese location token, or English role terms require an English location token.

For a Chinese user request targeting Shanghai, the initial plan contains these twelve queries:

1. `上海 AI Agent 工程师 招聘`
2. `Shanghai AI Agent 工程师 招聘`
3. `上海 智能体工程师 招聘`
4. `Shanghai 智能体 Engineer jobs`
5. `上海 大模型应用工程师 招聘`
6. `Shanghai 大模型应用工程师 招聘`
7. `上海 生成式 AI 工程师 招聘`
8. `Shanghai Generative AI Engineer jobs`
9. `上海 AI Agent Engineer jobs`
10. `Shanghai AI Agent Engineer jobs`
11. `上海 LLM Application Engineer jobs`
12. `Shanghai LLM Application Engineer jobs`

The planner returns an ordered, deduplicated tuple and records why expansion occurred. The original profile query remains diagnostic input but does not replace this required Shanghai matrix.

## Request Budget and Localization

Each query can issue one `google_jobs` request and one `google` request. The hard ceiling is therefore 24 SerpAPI requests per Shanghai search.

Requests use:

- `location=Shanghai, China`
- `hl=zh-cn`
- `gl=cn`
- `google_domain=google.com`

Concurrency is bounded rather than launching all requests without control. All twelve planned variants run against both engines so the location/role cross-language coverage is deterministic. Individual request failures are retained as safe diagnostics and do not discard successful results from other queries.

The tool input schema is extended with optional `query_variants`, `hl`, `gl`, and `google_domain`. Values are validated against bounded lengths and allowlisted locale/domain forms. API keys remain internal and never appear in result data or diagnostics.

## Aggregation and Deduplication

Every parsed result carries:

- `matched_queries`: ordered query variants that produced the result;
- `search_engines`: `google_jobs`, `google`, or both;
- original provider positions;
- source and retrieval timestamp.

Results are deduplicated first by canonical URL. Canonicalization removes fragments, normalizes scheme and host casing, and preserves non-sensitive query parameters needed by job pages.

Probable mirrors of the same job are grouped by normalized title, company, and location. Within a mirror group, preference is:

1. employer-owned job-detail page;
2. ATS or recruitment-board detail page;
3. aggregator page.

Distinct jobs are emitted before secondary mirrors.

## Ranking

Ranking uses one relevance score before link-kind tie breakers. Positive signals include:

- explicit Shanghai location;
- `上海` or `Shanghai` in title, snippet, or location;
- Chinese title;
- `智能体`, `大模型`, `生成式 AI`, `AI 应用`, `算法工程师`, `AI Agent`, or `LLM Application` relevance;
- employer-owned detail URL;
- job-detail URL shape;
- both responsibility and requirement signals in the snippet;
- structured apply metadata.

Negative signals include:

- a clearly non-Shanghai location;
- generic Careers or Join Us pages;
- collection or search-result pages;
- login, expired, unavailable, 404, forbidden, or error signals;
- very short snippets with no job-detail evidence;
- aggregator domains such as BuiltIn when a usable employer or ATS mirror exists.

Every score change adds a stable `reason_code`. The top-ten diagnostic output includes URL, title, score, page kind, reason codes, matched queries, and engines. Domain signals adjust ordering but do not permanently block a domain.

## JD Retrieval and Chinese Extraction

Ranked candidates continue through the existing reliability pipeline:

- at least 15 seconds initial Playwright wait;
- stable snapshot validation;
- one retry with a longer wait;
- safe HTTP and JSON-LD/HTML fallback;
- search snippet as partial evidence.

Partial evidence never counts toward the verified-JD target. Candidate iteration continues until the verified target is reached or candidates are exhausted.

HTML, plain-text, and Playwright snapshot extraction recognize:

- `岗位职责`
- `工作职责`
- `职位描述`
- `任职要求`
- `岗位要求`
- `职位要求`

Anti-crawl failures preserve exact safe codes such as `access_blocked_403`, `playwright_timeout`, `selector_unmatched`, and `browser_crashed`.

## Output Contract

The public response renders three independent sections:

1. verified JD previews;
2. partial search evidence;
3. failed URLs with exact safe failure codes.

Each partial record displays title, company/location when available, retrieval method, snippet, and URL. If four partial records exist but only three are rendered, the heading says `部分岗位证据共 4 个，以下展示前 3 个`.

Search diagnostics include:

- planned query count;
- executed query count;
- SerpAPI request count;
- raw result count;
- canonical-URL deduplicated count;
- Chinese-title result count;
- verified JD count;
- partial evidence count;
- failed URL count.

## Testing and Evidence

TDD coverage must demonstrate:

- a Chinese Shanghai request produces both `上海` and `Shanghai` query variants;
- the twelve required variants are ordered and deduplicated;
- localized parameters reach both SerpAPI engines;
- multiple-query results merge and deduplicate while retaining provenance;
- Shanghai Chinese Agent/AI details outrank non-Shanghai English aggregators;
- employer details outrank aggregator mirrors;
- Chinese responsibility and requirement headings extract correctly;
- partial counts distinguish total from displayed records;
- verified jobs remain visible alongside partial evidence and exact per-URL failures.

Fixed SerpAPI fixtures provide deterministic before/after recall metrics. The final report includes the actual query plan, localized parameters, top-ten score diagnostics, Chinese-title recall before and after, and verified/partial/failure counts. Live Google results are supplemental evidence only because they change over time and may be unavailable in the execution environment.

## Safety and Compatibility

- All external calls continue through the governed tool executor.
- Query expansion contains public job terms only and does not copy resume text into SerpAPI queries.
- No API key, authorization header, resume content, or raw external page is added to diagnostics.
- Existing non-China single-query behavior remains supported.
- Existing Playwright and HTTP safety controls remain unchanged.
